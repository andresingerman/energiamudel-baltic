This is the binding document of the project. Every requirement carries an identifier. Where another document of this repository disagrees with this one on a requirement, this document wins; where it disagrees on process, `AGENTS.md` wins. Changing a requirement means a new revision of this document and a record in `DECISIONS.md`.

The document is written for a stranger: someone who has only this repository and wants to check whether the model does what it says.

## 1. Purpose of this document

energiamudel v5 is an hourly day-ahead market model of the three Baltic bidding zones — Estonia, Latvia, Lithuania — with Estonia in focus, built for Estonian energy-sector stakeholders. It exists to answer two questions under assumptions the user sets and can see:

1. What a small modular nuclear plant (SMR) in Estonia does to the Baltic price, energy balance and import dependence, and what a contract for difference on it costs the state.
2. What happens to Baltic prices when interconnectors fail, are limited, or are added.

The model combines what worked in v3 (a fast, pure, deterministic engine running in the browser; an interface stakeholders used) with what worked in v4 (an API-first data pipeline in which every number carries a provenance record; a specification-and-decisions discipline; a control panel designed around the questions above). It abandons what did not work in either: v3's hand-set neighbour multipliers and manual CSV downloads; v4's nine-zone linear programme that never met its own calibration gate and never reached the browser.

The repository is built to be published for independent review. Everything in it is written so that a reviewer can walk any number back to the API call or the document page it came from.

## 2. Terms

| Term | Meaning in this document |
|---|---|
| **Core zone** | EE, LV, LT — a bidding zone whose supply, demand, storage and price the model computes. |
| **Boundary zone** | FI, SE4, PL — a neighbouring bidding zone represented by an exogenous hourly price profile and an hourly transfer capacity, not by a fleet. |
| **Observed year** | A calendar year for which ENTSO-E and TSO data exist (2020 → today). Used for calibration and replay. |
| **Climate year** | One of the weather years 1995, 2008, 2009 of the Pan-European Climate Database (PECD) used by ENTSO-E TYNDP 2024. Used for scenario years. |
| **Replay** | A model run on an observed year with observed fleet, demand, fuel prices, neighbour prices and transfer capacities. Comparable with observed prices. |
| **Scenario** | A model run on a documentary fleet and demand (a TSO or ENTSO-E scenario, or the owner's), on a climate year. Not comparable with any observed price. |
| **Lineage record** | The JSON record written at the moment of fetching a dataset: source, endpoint, parameters, fetch time, HTTP status, SHA-256 of the raw file, licence. Every fact row in the database carries its id. |
| **Documentary source** | A published document read by a person (a TSO plan, an ENTSO-E scenario workbook, a regulator's report, a press release). Cited to document and page in `data/documentary/*.csv`. |
| **Gate** | A measurable condition that must hold before the next stage starts or a result is released. Gates are listed in §14. |
| **Owner** | Andres Ingerman. The owner signs this document, decides open parameters, decides publication. |
| **Working document** | Any document the repository generates that carries numbers. While a gate is unmet, every working document states so in its first lines. |
| **NTC** | Net transfer capacity offered to the day-ahead market on a border, per hour and direction (ENTSO-E 11.1/12.1, document type A31/A61). |
| **VOLL** | Value of lost load: the price at which the model sheds load. Set to the SDAC harmonised maximum clearing price (§8.9). |

## 5. Claims the model must not make

These are false, and each would be a natural thing to assume if nobody had written it down.

1. **That v5 reproduces observed history as accurately as v3's published fit (hourly MAE 8–12 €/MWh on 2023–2025).** v3's neighbour border was anchored at the observed price and flow of the Baltic node in every hour, so the observed price entered the model as an input. v5 forbids that (`R-BND-3`) and is measured against its own thresholds (§9). A comparison of MAE figures across the two models is not a comparison of accuracy.
2. **That any single climate year's result is "the 2035 price".** 2009 is the calmest wind year of 38 for Estonia (PECD onshore capacity factor 0.213, rank 1 of 38; 1995 and 2008 rank 36 and 37). A result is a set of three years with ENTSO-E's weights, or nothing (`R-TIME-4`).
3. **That a result computed with a non-zero boundary slope is the model's answer.** The slope is a sensitivity around the price-taker base case; no published market model implements an elastic exogenous border, and the slope's estimation is documented with its uncertainty (`R-BND-6`).
4. **That the two-pass engine is the model's answer.** Its storage dispatch was an approximation whose gap to the LP was published for every release (`R-ENG-8`), and the application did not show it (*revision 1.5*); since *revision 2.19* it is removed (D-132); every published, exported or calibrated figure comes from the weekly LP, which itself assumes perfect foresight within each week and storage empty at each week's start and end (*revision 1.4*) — *revision 2.8 (D-112):* foresight of the day and the next, each day's window ending its stores empty and the day's energy carried to the next.
5. **That the plant's annual output is an input.** Under a contract with a negative-price clause the plant curtails; its capacity factor is a result (`R-SMR-4`).

## 6. System context

Two execution contexts that never mix.

**Build time** is Python on a maintainer's machine: fetch from public APIs and record provenance (`pipeline/`), build the DuckDB database from the raw cache (`db/`), fit the calibration parameters and run the offline LP reference (`reference/`), export compact per-year JSON files with a manifest (`export/`), run the validation protocol, commit the outputs. Build time may use gigabytes of memory and hours of wall clock.

**Run time** is the visitor's browser reading static files from a web host. No server computes anything. The engine (`app/src/engine/`) is a pure function from (year data, scenario) to results, executed in a Web Worker. The application never calls a network endpoint other than its own static files.

```
public APIs and documents
        │  pipeline/  (Python: fetch, lineage record per dataset, register)
        ▼
data/raw + data/lineage   (git-ignored cache, refetchable; ~7 GB)
        │  db/        (DuckDB rebuilt by one command; every fact row → lineage_id)
        ▼
data/energiamudel.duckdb
        │  export/    (per-year JSON + manifest.json with lineage ids; ≤ 3 MB gz per year)
        │  reference/ (offline LP on the same weeks → gap table)   validate/ (protocol of §9)
        ▼
app/public/data/            (committed)
        │  app/src/engine/  (TypeScript, pure, deterministic, Web Worker)
        ▼
app/                        (Vite build → static site → v5.energiamudel.ee)
```

**Repositories.** `energiamudel-v5` (this one, new, D11). `energiamudel-v4` is archived read-only as the reference model; its lineage-bearing raw cache is migrated (Appendix A). `energiamudel` (v3) stays deployed at the root domain until promotion (§13.3).

## 7. Data layer

**R-DATA-1 · Sources.** Measured data comes from public APIs or public files: ENTSO-E Transparency Platform (prices A44, load A65, generation per type A75, installed capacity A68/A71, production and generation units A95, reservoir filling A72, physical flows A11, offered transfer capacity A31 (A61 is empty on these borders), transmission and generation unavailability A78/A80, day-ahead net positions and scheduled exchanges — 12.1.E/12.1.F), Fingrid Open Data, the Baltic Transparency Dashboard, JAO Nordic Publication Tool, Nord Pool REMIT UMM API, TYNDP 2024 scenario files (PECD, PEMMDB, demand profiles, hydro inflows, market-model outputs), ERAA 2025 files (hourly NTC package, dashboard data), EEX EUA primary auctions, World Bank Pink Sheet, Open-Meteo ERA5, the Danish Energy Agency technology catalogue, Statistics Finland's fuel classification, and the published documents cached with a lineage record each (`pipeline/sources/documents.py`). ECB rates and Energimyndigheten served fleets v5 does not model and are not used (DECISIONS D-002). Documentary sources are listed in `data/documentary/*.csv`. The full list with access conditions, licence and use is `docs/SOURCE_REGISTER.md` (§10).

**R-DATA-2 · Coverage.** Observed data for EE, LV, LT, FI, SE4, PL from 2020-01-01 to the latest complete month, hourly. Borders: EE–FI, EE–LV, LV–LT, LT–SE4, LT–PL in both directions. Climate-year data for the three PECD years: capacity factors, demand profiles and hydro inflows for EE, LV, LT; market-model prices for all six zones; per boundary scenario, the annual demand and electrolysis it assumes for FI, SE4 and PL (`R-BND-8`).

**R-DATA-3 · Lineage.** One lineage record per fetched dataset, written at fetch time, in the format of v4's `pipeline/lineage.py` (`dataset, source, endpoint, params` with the token stripped, `fetched_at, http_status, sha256, rows, licence, derived_from, notes`; `page` for documentary sources). Every fact row in the database carries a `lineage_id`. The database build fails if any row lacks one.

**R-DATA-4 · Time.** Timestamps are UTC and mark the start of the interval, everywhere. Fifteen-minute series are averaged to hourly. Conversion to Estonian local time happens only at display. Every hour of every year is present, including the DST transitions; `make check` proves it.

**R-DATA-5 · Idempotence.** A fetcher never re-downloads an existing raw file. Rebuilding the database from the same cache produces a byte-identical database. Rebuilding the export from the same database produces byte-identical export files.

**R-DATA-6 · Register before use.** A source is not read by any code until it is in `pipeline/register.py` with its purpose, licence and access conditions. Adding a fetcher or a documentary CSV means adding its register entry in the same commit. `make smoke` proves every configured source with one small real fetch.

**R-DATA-7 · Documentary inputs.** Forward-looking fleets, demand, links and fuel paths come from published documents and live in `data/documentary/*.csv`, each row citing document, edition, page (or table) and URL. A PDF read by a person is kept in `data/raw/doc/` (git-ignored) with its lineage record. The v4 files `scenarios.csv`, `links.csv`, `fuel_paths.csv`, `tech_parameters.csv` are imported (D11); `parameters.csv` holds scalar parameters and validation targets. Every row of every documentary CSV has a verification record in `verification.csv` — re-extracted by code for rows taken from a fetched file, re-read on the cached page for the others (DECISIONS D-006) — and `make check` fails on a row without one or on a value changed after it was verified.

**R-DATA-8 · Export.** Per year (observed or climate), one JSON file with: hourly load per core zone; hourly must-run and capacity-factor series per technology per core zone; hourly boundary prices for FI, SE4, PL; hourly NTC per border and direction; hourly reserve procured per zone and product (observed years) or the documented reserve need (scenario years); weekly hydro budgets; plus `manifest.json` listing, for every series, the lineage ids it derives from and the export's own hash. Compressed size ≤ 3 MB per year (`R-NFR-4`).

**R-DATA-9 · Raw cache.** Git-ignored. Refetchable from an empty clone with `make history` (needs the ENTSO-E token and the Fingrid key in `.env`, never committed). Migration from v4 (Stage 2) copies only files that have a lineage record and verifies each file's SHA-256 against it; a file without a record is not migrated.

**R-DATA-10 · Restricted data.** No restricted or paid data is required. Nord Pool's aggregated bidding curves are visible without login for the latest delivery day only; their history needs a paid Data Portal subscription (2026: €1 200 per year for one user) or Nord Pool's curves product, with special terms for researchers on inquiry (ERRATA E-019). The owner asks for those research terms first; the paid curve API (Baltic cluster and Finland, €430 per year each) is bought only if they are refused (revision 1.3, D-011). If access is obtained (OPEN-10), the curves are used only to derive and cross-check parameters (`R-BND-6`, `R-SUP-6`); the curves themselves are never committed, and the derivation records the export date and the terms as read on that date. Without access those two steps keep their documented defaults and say so. The Fermi Energia operating-model figures behind the contract defaults are restricted; the model runs and the documents read correctly without them (`R-SMR-7`).

## 8. Model

### 8.1 Boundary zones (D2)

**R-BND-1 · Representation.** Each boundary zone k ∈ {FI at EE; SE4 and PL at LT} is an exogenous hourly price series P_k[h] and, per direction, an hourly transfer capacity NTC_k[h]. The flow on the link is a decision of the clearing, not an input.

**R-BND-2 · Price-taker rule (default).** The boundary offers to export into the Baltic node any quantity up to NTC_k^import[h] at price P_k[h], and to absorb any quantity up to NTC_k^export[h] at price P_k[h]. Implementation: a supply block from 0 to NTC_import at P_k and a demand block from 0 to NTC_export at P_k, each ramping over a band of 1 €/MWh so that the node's net-export function stays continuous and monotone (v3's ramp band). When the link is not saturated the Baltic node's price equals P_k[h]; when it is, the node's price departs from P_k[h] and the link sits exactly on ±NTC.

**R-BND-3 · No historical anchor.** No observed flow and no observed price of the core zone enters the boundary formulation. In calibration years P_k is the observed price at the boundary zone's end of the link: the zone's day-ahead price (ENTSO-E A44 for FI, SE4, PL) and, where the market couples the link at a virtual hub of a flow-based region, that hub's price as the region's published shadow prices and PTDFs give it (SE4_NB and FI_EL from the Nordic go-live of 2024-10-29; the link's own constraints left out), and, for a zone whose net position the market limits by an allocation constraint, the zone's price less that constraint's shadow price as the region's published prices, shadow prices, PTDFs, net positions and limits give it (Poland from the Core go-live of 2022-06-09; *revision 1.9, D-075, D-076*). No observed price, flow or schedule of a core zone enters it. This is what makes the fit of §9 a test.

**R-BND-4 · Losses.** HVDC transmission losses are a documented parameter per link (default from the ENTSO-E HVDC statistics 2024: each direction's losses over the energy sent, losses included — EstLink 1 and 2 together 4.0 % towards Finland and 3.6 % towards Estonia; the other links per the same report; *revision 1.7*, ERRATA E-028), applied to the importing side. *Revision 2.0 (D-042, D-045; ERRATA E-056):* the day-ahead coupling applies no loss factor on EstLink, NordBalt or LitPol (Nord Pool's loss functionality covers other cables), and where a cable is below its limit the two zones clear at one price to the cent; replays and scenario runs therefore clear without the wedge. The parameter stays in the engine's scenario for a sensitivity; the application has no control for it.

**R-BND-5 · Scenario-year profiles.** For climate years, P_k is the TYNDP 2024 market-model hourly price for the zone's node, scenario (Distributed Energy / Global Ambition / National Trends) and target year chosen by the user, in the **same climate year as the Baltic weather** (D3). All published outputs for the six zones are in the database (`tyndp_price`, Stage 2): National Trends 2030 and 2040 for climate year 2009 only; Distributed Energy and Global Ambition 2035, 2040 and 2050 for all three climate years. Only the latter two can be weather-coherent for 2035; National Trends 2040 holds 226 (EE) to 458 (PL) hours at or above 500 €/MWh (DECISIONS D-007, OPEN-8). The TYNDP 2026 family takes P_k from the National Trends+ hourly dashboards of the same weather scenario as the Baltic inputs (D-010); National Trends 2030/2040 of TYNDP 2024 remain a labelled single-climate-year option of the first family. The user may rescale a profile by a level factor; the factor is shown next to the result and defaults to 1. For Poland the factor has a documented slow-build value, 1.4, which only the standard sensitivities use (`R-APP-11`), never a headline: Svenska kraftnät's lowest 2040 annual price for Poland across its four scenarios, 77.8 €/MWh (Långsiktig marknadsanalys 2026, Figur 31, p. 79; its highest, 83.6, would give 1.5), over the weather-weighted TYNDP 2026 National Trends+ 2040 wholesale average of 55.5 €/MWh (`tyndp2026_price`). On the default profile (Distributed Energy 2035, weighted average 57.2 €/MWh) it gives about 80 €/MWh; Poland's observed 2025 average was 104.3 (revision 1.3, D-011). *Revision 2.11 (ERRATA E-149; approved, D-124):* the standard sensitivities hold Poland's average at Svenska kraftnät's lowest 2040 price itself, 77.8 €/MWh, by one factor on every hour of a run where the profile's average is lower: the factor of 1.4 multiplied the re-priced default, already at 78.6, to 110. Any other profile (e.g. an observed year rescaled) is a documented option, labelled as such. The application opens on the TYNDP 2024 family, Distributed Energy 2035 on 1995/2008/2009; Global Ambition 2035 is the alternative profile the user selects, not a fifth standard sensitivity (*revision 1.7*, ERRATA E-031), and TYNDP 2026 National Trends+ the second family (owner, revision 1.3, D-011; OPEN-8 closed). *Revision 1.6 (D-036):* the scenario view offers Distributed Energy 2035 and Global Ambition 2035 of TYNDP 2024 and National Trends+ 2035 of TYNDP 2026, one choice for the three boundary zones, each keeping its level factor; it opens on Distributed Energy 2035. The National Trends 2030/2040 option leaves the application. ### 8.2 Time base (D3)

**R-TIME-1 · Observed years.** Calibration and replay use observed years. Parameters are fitted on 2023–2024 and tested blind on 2025 (`R-VAL-1`). 2020–2022 are diagnostic (`R-VAL-7`). 2026 enters as a second blind year month by month as data completes; a partial year is replay-only.

**R-TIME-2 · Climate years.** Scenario runs belong to one of two families (D-010). **TYNDP 2024:** the PECD climate years 1995, 2008 and 2009 — the three TYNDP 2024 uses, selected by ENTSO-E for TYNDP 2022 among the thirty years 1987–2016 by the residual-load method of the TYNDP 2022 System Needs Study guidelines §6.2–6.3 and kept for 2024 (*revision 2.1*, `R-APP-13`, D-084; the 2024 guidelines say "out of 35", the years PECD then held; the export holds 38, 1982–2019). **TYNDP 2026:** the three weather scenarios National Trends+ uses for the target year (2030: WS003, WS021, WS029; 2035: WS032, WS037, WS059; 2040: WS065, WS071, WS077; 2050: WS091, WS092, WS106), modelled years of CMIP6 SSP2-4.5 projections in PECD 4.2. In either family all weather-dependent inputs come from the same year or scenario: wind and solar capacity factors (PECD, per core zone and per technology), demand shape (TYNDP demand profiles), hydro inflow (TYNDP hydro inflows for LV and LT), boundary prices (TYNDP market-model outputs, `R-BND-5`). Each family takes these from its own TYNDP edition; a run never mixes them. *Revision 1.6 (D-036):* the application's scenario runs take the target year 2035 only; choosing National Trends+ switches the run to the TYNDP 2026 family — its weather scenarios and its own Baltic demand, the fleets staying the scenario's.

**R-TIME-3 · Weights.** ENTSO-E's weights for the three climate years are 0.233 (1995), 0.367 (2008), 0.400 (2009) (TYNDP 2024 Implementation Guidelines, version for ACER's opinion of 2025-04-09, p. 12; the 2024 draft prints the same). In the TYNDP 2026 family the weights are those of the Methodology Report, Table 36 (2030: WS003 0.63, WS029 0.30, WS021 0.07; 2035: WS037 0.43, WS059 0.33, WS032 0.24; 2040: WS077 0.40, WS071 0.40, WS065 0.20; 2050: WS092 0.57, WS091 0.23, WS106 0.20), loaded from the report's data tables. The weighted average of the three runs is the headline; the three runs are always shown beside it.

**R-TIME-4 · Labelling.** Each climate year is labelled in the interface by its rank among the 38 PECD years for the quantity that matters to the reader: for Estonia, onshore wind capacity factor (1995: 0.283, rank 36/38; 2008: 0.285, rank 37/38; 2009: 0.213, rank 1/38, the calmest), solar (2008 rank 2/38, the dullest), and demand-shape peak (1995 and 2008 mild, 2009 median). The ranks are computed from the PECD tables in the database and stored in the export manifest. A TYNDP 2026 weather scenario is labelled by its code, climate model and modelled year (e.g. "WS037, CMCC-CM2-SR5, 2036") and by its Estonian wind and solar capacity factors; it is never presented as a historical year.

**R-TIME-5 · PECD versus observed.** PECD capacity factors are for a reference fleet and differ from the observed fleet's. Stage 2 computes, per core zone and technology, the ratio of observed capacity factor (ENTSO-E A75 over A68) to PECD's for the overlap years 2015–2019 (PECD 3.1 ends in 2019; DECISIONS D-005) and compares 2020–2025 with the PECD climatology; the result is `methodology.md` §2 (2020–2025: Estonian wind 0.98, Estonian solar 1.07, Lithuanian wind 0.61 — a reference fleet of modern turbines against an older observed fleet). Whether a correction is applied is decided by the owner on that evidence (OPEN-2).

**R-TIME-6 · Hourly.** The model is hourly. Leap years have 8 784 hours. Cross-year series of different lengths are never wrapped by index; a run uses one year's data for every input.

### 8.3 Engine (D4; revision 1.4: the engine of record and the preview; revision 1.5: the application shows the engine of record only; revision 2.19: the preview removed)

**R-ENG-1 · Location and purity.** The engine runs in the browser, in Web Workers, as pure functions `run(yearData, scenario) → results` — the engine of record (`R-ENG-8`), with the solver passed in (until *revision 2.19* also the two-pass engine of `R-ENG-2` … `R-ENG-5`, called the preview in revision 1.4 and a baseline the application did not show since revision 1.5; removed, D-132): no DOM, no fetch, no clock, no randomness, no hidden state. Identical inputs give byte-identical outputs (`R-NFR-5`).

**R-ENG-2 · Clearing in the preview.** *Retired in revision 2.19 with the two-pass engine (D-132); as it read:* For every hour, the three core zones and their boundary blocks are cleared on the tree FI—EE—LV—LT—{SE4, PL} by the v3 method: each zone's net-export function is continuous and monotone in price (blocks ramp over 1 €/MWh); a segment of the tree is cleared by bisection on [floor, VOLL]; when an internal border's flow exceeds its NTC the border is fixed at ±NTC and the two halves are cleared recursively. Prices are equal across an uncongested segment and diverge exactly when a border saturates. If a segment cannot be served at VOLL, load is shed at VOLL and the shortfall is attributed per zone in proportion to its own deficit.

**R-ENG-3 · Storage in the preview, pass one.** *Retired in revision 2.19 with the two-pass engine (D-132); as it read:* With storage removed, the year is cleared to obtain prices p⁰. For each storage unit (battery fleet per zone, pumped hydro), a dynamic programme over (hour × state of charge) against p⁰ yields a candidate schedule under: power and energy bounds, round-trip efficiency η, cycling cost Δ per MWh charged (a cycle is taken only if p_discharge·η − p_charge ≥ Δ), and the daily cycle cap (`R-PAR-5`). This is v3's `simulateBattery` (exact DP, SoC-feasible, multi-cycle), reused with attribution.

**R-ENG-4 · Storage in the preview, pass two: price-responsive bids.** *Retired in revision 2.19 with the two-pass engine (D-132); as it read:* The year is cleared again with each storage unit present as bids rather than fixed injections: in an hour the schedule discharges, the unit offers up to that quantity at a floor price equal to the cost of the energy it holds (the charging prices paid plus Δ, divided by η; *revision 1.4*, ERRATA E-034); in an hour the schedule charges, it demands up to that quantity at a ceiling equal to the value of the later discharge times η minus Δ. The clearing may reduce either quantity. State of charge is tracked hour by hour in the second pass; a discharge is capped by the energy actually stored; an hour whose schedule cannot be honoured is recorded. There is no third pass. The residual between schedule and realisation (MWh, per unit, per year) is a reported result.

**R-ENG-5 · Reservoir and pumped hydro.** The Daugava cascade (LV) is dispatched by a weekly energy budget: observed weekly generation in calibration years, TYNDP inflow of the climate year in scenario years. In the preview the budget was released within the week by a storage-value rule against the pass-one prices (the highest-price hours first, subject to turbine limits and a documented minimum flow), then entered pass two as price-responsive bids like a battery (removed in *revision 2.19*, D-132). Kruonis (LT) is closed-loop pumped storage without inflow and is dispatched like a battery (`R-ENG-8`; `R-ENG-3`, `R-ENG-4` until *revision 2.19*), with cycle efficiency 0.74 (v4 D-053, Ignitis) and, in calibration years, its observed weekly generation as a cap on its discharge (*revision 1.4*, ERRATA E-030). In the engine of record both are variables of the weekly LP under the same budgets and limits — since *revision 2.8 (D-112)* of each day's window of it (`R-ENG-8`), the week's budget shared out by the hours left. No water-value model across weeks. *Revision 2.0:* in a replay the cascade releases, hour by hour, between the 10th and the 90th percentile hour of the week's observed output (D-044), and Kruonis delivers at most the week's maximum observed output and pumps at most that over its efficiency (D-073); in a scenario year the cascade's weekly energy is TYNDP 2024's inflow times the record's ratio over the years both cover (1.95; D-070, ERRATA E-063), the workbook's "maximum generating power" is not read as a limit, and the hourly output is held to the band the record shows for a week of the same average (D-071). *Revision 2.9 (D-115):* Kruonis's output in an hour runs in four equal segments of the power it has that hour, the first at the plant's cost and each further one a step more, the step fitted with the markup (`R-VAL-1`, `R-PAR-10`); its reservoir, its pumping and its budgets stay one. The programme spreads the plant's water over more hours at part load and gives the dearest hours less than its power allows, as its owner, who weighs what its output does to the price, runs it.

**R-ENG-6 · Flexible demand.** Electrolysis and power-to-heat are price-responsive demand blocks with a documented ceiling price (`R-DEM-5`); explicit DSR is a set of price bands from ERAA/PEMMDB (`R-DEM-6`); both enter the clearing directly. Implicit within-day load shifting is not modelled.

**R-ENG-7 · Performance.** The engine of record completes a year in ≤ 2 s and the three years of a scenario set in ≤ 6 s on four workers (measured in M2 on the development machine: 0.35 s for the 2024 replay, 0.56 s for climate year 2009 with ERAA 2035's four storage units and 1.45 s for the three climate years, worker start and problem builds included; measured on the built site in M7). Recompute is debounced; a progress indication appears while the engine of record runs, and its result replaces the previous one when it arrives (*revision 1.5*). Revision 1.4 showed the two-pass engine at once as a preview; with M3's inputs it missed whole years by 40–50 €/MWh, and a corrected version (the Daugava's price response from five clearings, storage planned in slices) took 0.7–0.8 s a year, no faster than the engine of record on four workers (ERRATA E-040, D-026). *Revision 2.15 (D-126):* the opening view — the four scenarios and the shown scenario's standard sensitivities — is computed by the engine of record when the site is built and shown without a run, for the build and the export it was computed from; a set the visitor's browser computed is kept in that browser and shown again without a run for the same build, export and settings. Any change of a control computes as above. *Revision 2.16 (D-127):* in the scenario view the scenario shown is computed first, then Elering: gas, then the other two; the scenario shown replaces the previous results when its years are in, each other scenario fills its columns of the table as it comes in, and the progress indication says how many years are still computing, the results under it dimmed as the previous settings' only until the scenario shown is in. *Revision 2.17 (D-129):* the states of the presentation of 10 November — the opening state's sensitivities for each scenario shown, and the neighbours' two tight profiles of 2035 with their four scenarios and each one's sensitivities — are computed by the engine of record when the site is built and fetched when first shown, for the build and the export they were computed from. *Revision 2.76 (D-232, D-233, D-237):* every set the page shows — the table's, the sensitivities', the presentation's blocks, the deck's outages and replays, a validation run's year — is kept by what it computes from, in the page's memory and in the reader's browser, the sets last used up to a budget of bytes, and shown again without a run; a set is kept, and the build's sets are read, for the sources that compute a set and the export they were computed from — an edit to the interface keeps them, and the development server keeps its sets as the site does; while another page than the Model view is shown the standard sensitivities are computed after that page's own sets.

**R-ENG-8 · The engine of record: the weekly LP (each week day by day since revision 2.8); the two-pass engine's gap until revision 2.19.** Every published, exported and calibrated figure comes from a linear programme of each week of the run (UTC weeks from the run's first hour, the last one shorter) — since *revision 2.8 (D-112)* each day of the week in a window of the day and the next (48 hours within the week), the day kept, the stores' energy and the week's unused budgets carried to the next day, a window's stores ending it empty and a budget that runs past it, the Daugava's among them, giving it its share by hours: the three zones' offers and fixed output, load shed at VOLL and output spilled at the floor, the boundary blocks and internal links, each storage unit's charge, discharge and energy (empty at the week's start and end, its daily cycle cap `R-PAR-5`, Kruonis's observed weekly output in calibration years), the Daugava's weekly budget and minimum flow, flexible demand and DSR hours per day, and reserve headroom; the prices are the duals of the zone-hour balances. It is solved by HiGHS compiled to WebAssembly (highs-js, version pinned) on up to eight Web Workers, one less than the machine's cores, each year's weeks shared among them (*revision 2.8*, D-114; four, a year each, until then), and by the same HiGHS in Python as the offline reference (`reference/lp.py`); `spikes/wasm-solver/` holds the measurements. The test weeks are at least one winter and one summer week of each calibration year, and the same weeks of one climate year with the ERAA 2035 fleet including 1 500 MW of Estonian batteries. The two-pass engine of `R-ENG-2` … `R-ENG-5` was not shown (*revision 1.5*); its gap to the programme on the test weeks — average absolute price difference per zone, storage discharge energy, congestion rent per border — was published in `methodology.md` for every release, without a gate, until *revision 2.19* removed it (D-132; the last gap stays in `methodology.md` §6). **Gate:** on every test week the engine of record reproduces the offline reference within 0.1 €/MWh average absolute price difference per zone and ±1 % storage discharge; where the prices differ beyond it, the week meets the gate on the same optimum — every window's objective within 10⁻⁶ of the reference's and the storage discharge within ±1 % — and the report lists the hours whose price is not unique (*revision 2.36*, D-175). Revision 1.3's gate on the preview (3 €/MWh, ±15 %) was met in one test week of eight (DECISIONS D-019, *revision 1.4*).

**R-ENG-9 · Determinism of the LP.** The LP is degenerate (many optimal dispatches). The engine of record and the reference apply the same deterministic cost perturbation per unit (v4 R-REF-5) with fixed solver options and one thread per solve, and report prices, not volumes, as the primary comparison quantity. *Revision 2.18 (D-130, D-131):* the fixed options set presolve off, and a programme left unsolved with them is solved again with presolve on, in both.

### 8.4 Baltic supply (D8)

**R-SUP-1 · Technology classes.** Per core zone: wind onshore, wind offshore, solar, hydro run-of-river, hydro reservoir (LV), pumped storage (LT), biomass CHP, gas CHP, gas condensing / peaking, oil shale (three classes, EE), shale (retort) gas (EE), waste, peat, other. Nuclear (EE, `R-SMR`). Batteries (`R-STO`). Installed capacities: observed ENTSO-E A68/A71 for observed years; documentary scenarios for scenario years (`R-DEM-1` lists the preset families). *Revision 1.6 (D-036):* S1's Estonian fleet for 2035 (pp. 2–3): onshore wind 1 244, solar 1 785, batteries 1 500 MW, biomass 152, waste 17, run-of-river 8, oil shale 270 (Auvere, which S3 names), and natural gas in four rows — existing 263, reserve procurement 186, the distributed restoration tender 900 and the future capacity mechanism 15 MW — the last two entered "simply as gas plants" (p. 3). v5 enters all 1 364 MW as the peaking class, in the market. ERR's report of the tender (2026-04-23) describes a restoration service paid outside the market; following S1 gives the gas its largest role in the market, the cautious choice for the plant's comparison.

**R-SUP-2 · Renewables.** Wind and solar are curtailable blocks at a bid of 0 €/MWh (`R-PAR-3`); output = capacity × capacity factor, where the capacity factor is observed (A75/A68) in observed years and PECD in climate years, with the documented PECD correction of `R-TIME-5` if adopted.

**R-SUP-3 · Fuel-based bids.** A thermal class bids its short-run marginal cost: fuel price / efficiency + CO₂ price × emission factor + variable O&M, plus the class's markup (`R-SUP-6`). Fuel and CO₂ prices are monthly: TTF natural gas from the World Bank Pink Sheet, EUA from the EEX primary auction clearing prices, both fetched by API with lineage. Prices the Pink Sheet publishes in US dollars are converted to euros at a monthly exchange rate with its own lineage (OPEN-13, ERRATA E-024). Efficiencies, emission factors and variable O&M come from ERAA 2025 common data and the Danish Energy Agency technology catalogue, cited per class. *Revision 2.4 (D-090):* in a scenario run the user may type another bid for a thermal class of a core zone (not waste, which runs whatever the price, nor the plant, whose units run as must-run); the run keeps the difference to the cost-based bid as an offset, so the bid follows the gas and CO₂ prices; the offset is added before the markup, the bid is held at 0 or above, and the scenario text carries it as `bid.<zone>.<class>`. A replay's bids are its costs alone. *Revision 2.30 (D-164):* the gas plants' one bid (`R-SUP-6`) is moved once for the three zones, the text carrying it as `bid.gas`; the panel shows it under the gas and CO₂ prices. *Revision 2.35 (D-171; ERRATA E-167):* the record's gas price is per gross MWh, as TTF trades and the Pink Sheet quotes it; ERAA states its efficiencies, emission factors and fuel prices on net calorific value (ERAA 2025 Annex 1, Table 8: "€2024/net GJ"). A replay therefore divides the record's price by 0.9, gas's net calorific value per gross (IPCC 2006 Guidelines, Volume 2, §1.4.1.2), and so does sensitivity (d) its shock (`R-APP-11`); a scenario's price, ERAA's, is used as it is.

**R-SUP-4 · Oil shale.** Three classes as in v4 D-062: `oil_shale_auvere` 270 MW (η 0.39), `oil_shale_cfb` 386 MW (η 0.34; Balti TG11 192 + Eesti TG8 194 MW, ENTSO-E A95, the two fluidised-bed units per Eesti Energia 2004), `oil_shale_pf` the remainder (η 0.29); CO₂ 100 kg/GJ; fuel 10 €/MWh thermal; each class carries a constant premium that lifts it to Eesti Energia's stated market-entry price at the 2024 average EUA price of 64.8 €/t (90, 110, ≥ 200 €/MWh; premiums +1, +9, +82 €/MWh), so the CO₂ part moves with the CO₂ price and the premium does not. Source: Eesti Energia's analysis as reported by ERR 2025-03-20; ENTSO-E A95; Enefit Power plant list; ERAA classes. Retort gas bids its CO₂ cost (v4 D-063). The strategic-reserve contract of 2025-12-01 leaves these units in the market (`R-PAR-9`). In a scenario year the oil shale is Auvere, a condensing unit, and carries no heat floor; the waste plants of every zone run as given output at their megawatts less the technology's outages (*revision 1.9, D-074*). *Revision 2.8 (D-113, D-114):* the classes enter the market by the UTC day, in replays and scenarios alike: the engine of record's first pass decides, per class and day, whether it runs — its price reaching the class's bid in at least ERAA 2025's minimum time on (8 h new, 11 h old) and, from off, the day's margin paying a warm start of the megawatts it has available that day (ERAA's cost and start fuel; D-114) — and a class on runs at least ERAA's minimum stable load (0.5) all day and offers the rest at its bid, a class off nothing; the second pass clears the committed problem; a replay's weekly least output (`R-SUP-5`) stays beneath. *Revision 2.18 (D-130, D-131):* a week in which the commitment keeps every class off and the first pass ran none of them is the first pass's in the second, its solution one of the committed week's optima. *Revision 2.31 (D-165; ERRATA E-160):* a day the second pass clears at the price cap in the entry's zone while the commitment keeps off a class that had megawatts available that day comes on — every such class at its minimum stable load all day, the rest at its bid — and the day's week clears again, until no such day is left; the next day decides as the rule does, the forced day not counting as a day on.

**R-SUP-5 · CHP must-run.** Heat-driven CHP output (gas and biomass CHP in all three zones) is a must-run quantity derived from ambient temperature (Open-Meteo ERA5, per zone) by a documented fit on observed years; not v3's monthly quantile. The fit is a calibration parameter (`R-VAL-2`): per zone and technology, the average hourly output of the fit years' hours whose observed price lay below the technology's cheapest bid, by temperature bin, a line on the bins' heating degrees (D-042; ERRATA E-057 — the envelope of revision 1.5 was a third of what runs unpaid). In a replay each thermal technology also runs at least the 10th-percentile hour of its week's observed output, and Kruonis at most its week's observed power; Estonian oil shale carries no fitted floor: in a replay the week's least output of its record holds the Narva plants' must-run, in a scenario year it has none (*revision 2.8*, D-109, D-110; before them the replay's oil shale carried the floor fitted on 2023–2024, *revision 1.9, D-073, D-074*).

**R-SUP-6 · Utilisation markup (disclosed).** A markup schedule by utilisation bin (0–50, 50–75, 75–90, 90–100 %) is added to the marginal cost of the flexible thermal offers, the gas classes, so the zone's supply curve is convex: each offer's megawatts left after the must-run floors (`R-SUP-5`; in a replay also the week's 10th-percentile hour of the record, D-073) and, in a scenario, the reserve headroom (`R-STO-7`) are split into tranches at those shares of the remainder's weekly maximum, each bidding the offer's cost plus its bin's markup (v4 D-032). One schedule serves Latvia and Lithuania; Estonia's gas carries none (D-073). *Revision 2.10 (D-117; ERRATA E-147):* the bins are each offer's remainder, as `applyMarkup` draws them; the text before it binned the utilisation of the zone's flexible fleet against the week's maximum, a form that fits the fit years 2.3 €/MWh worse (`docs/research/2026-10-11_dear_hours.md` §5). The schedule is fitted on 2023–2024 residuals, frozen, and tested blind on 2025; it is published as a table zone × bin × €/MWh with the fit years and the blind-year residual. It is cross-checked against the shape of the Baltic aggregated supply curve on the Nord Pool Data Portal for a sample of days if access is obtained (OPEN-10), and the comparison is published (`R-DATA-10`); without access the check is reported as not done. Nothing else in the supply side is fitted. *Revision 2.30 (D-164):* one bid for the gas of the three zones replaces the schedule: every gas offer — what the floors and the headroom leave of it — bids a combined-cycle plant's cost as the run prices it plus one adder, the same in every hour, zone and share of its output in use, whatever the plant's own efficiency. The adder is fitted on 2023–2024 together with Kruonis's step as the schedule was (each fit year's own adder, the register their average), frozen, tested blind on 2025, and published with its fit years and the blind-year residual; the cross-check against the curves applies to it. *Revision 2.33 (D-168, signed by D-169; ERRATA E-161):* among the equal bids the cheaper plant runs first: each gas offer's bid, hour by hour, is the one bid plus a thousandth of its class's cost above the combined-cycle plant's, so that the solver's tie-break on the offers' names no longer orders the zones' gas; no price moves by more than that term.

**R-SUP-7 · Reserve headroom.** Flexible thermal units and storage keep the upward reserve of `R-STO-6` as headroom below their availability in every hour.

**R-SUP-8 · Scenario fuel paths.** For scenario years, fuel and CO₂ prices come from one documented path per run (`data/documentary/fuel_paths.csv`: SvK LMA, ERAA 2025, IEA WEO 2025, Ramboll 2025 for Estonia — with pages). The CO₂ and gas sliders move the chosen path; their reference values are the path's, not constants.

**R-SUP-9 · Delivery variant.** Every fleet preset of a scenario year has a *delivery* variant: the preset with three classes limited to what the build record of 2021–2026 supports (owner, revision 1.3, D-011; evidence in `docs/research/2026-09-24_demand_and_buildout_realism.md` §2 and its appendix D). The variant never adds capacity to the preset.
- *Onshore wind:* the lower of the preset's value and a delivery path: WindEurope's expectation for 2030 (EE 920, LV 1 350, LT 4 230 MW; *Wind energy in Europe: 2025 statistics and the outlook for 2026–2030*, February 2026, Table 4, p. 44), plus, for each year after 2030, the zone's average net additions of 2021–2025 (EE 78, LV 11, LT 394 MW a year; IRENA, *Renewable capacity statistics 2026*, p. 18). For 2035 the path gives EE 1 310 MW against ERAA's 3 000; the paths of LV (1 405) and LT (6 200) lie above their presets, which then stand.
- *Offshore wind:* only projects with an awarded support contract; at this revision Lithuania's first 700 MW, awarded in 2023, of which WindEurope expects 630 MW by 2030 (the commissioning date is checked when the row is added). No other Baltic project has a support scheme in force, and none can be in service before about 2033: Poland's 2025 auction allows seven years from award to first power. From 2033 the preset's other offshore capacity is a switch, off in this variant.
- *Batteries:* the lower of the preset's value and the zone's installed and contracted fleet. Estonia: about 227 MW / 453 MWh (Auvere 26.5 MW / 53.1 MWh; Hertz 1 and Hertz 2, 100 MW / 200 MWh each, the second due at the end of 2026), held in every target year as a lower bound. Lithuania: 2 390 MW (690 MW installed on 2026-06-29 plus 1 700 MW / 4 000 MWh of the investment-support scheme), so ERAA's 1 750 stands and Litgrid's 3 099–4 397 are cut to it. Latvia keeps its preset: the research found no evidence on its pipeline either way.

Solar and every other class keep the preset's values: solar is at or ahead of the scenarios in Latvia and Lithuania and near TYNDP 2024's 2030 value in Estonia. The rows enter `scenarios.csv` with verification records in M1 (D-006).

**R-STO-5 · Reserve principle.** Capacity sold in the Baltic balancing capacity market (live since 2025-02-04) is not offered day-ahead. In every hour each core zone holds its upward reserve (FCR + aFRR up + mFRR up) out of the day-ahead market as headroom of its flexible fleet (v4 D-055/D-057).

**R-STO-6 · Reserve quantities.** Observed years from 2025-02-04: the Baltic Transparency Dashboard's procured-capacity reports, hourly (v4 cache; 2025 averages EE: FCR 7, aFRR 8 up / 10 down, mFRR 252 up / 76 down MW; LV: 14, 31/28, 6/8; LT: 3, 38/38, 414/390). 2026 and scenario years: the Baltic TSOs' published demand (Elering 2025-11-07: FCR 28 MW; aFRR 96–120 up / 104–120 down; mFRR 580–604 up / 675–691 down; about 1 600 MW in all), allocated to zones by the 2025 procurement shares, editable per zone, replaced when a TSO publishes a later need.

**R-STO-7 · Who holds it.** FCR and aFRR are assigned to batteries (the Nordic TSOs' April 2025 report shows batteries prequalified almost only in FCR/FFR; Baltic FCR and aFRR-down capacity prices fell from about 97 and 127 €/MW·h at market launch to about 48 and 9 €/MW·h by early 2026 as batteries filled a small demand). mFRR is split between batteries and thermal units by a share parameter: the owner's 0 (OPEN-3, D-025; *revision 2.8* — 50 %, labelled "estimate", was the default until then and stays in the register as evidence). A battery's day-ahead power is installed power minus its reserved power; Δ and the cycle cap apply to the remainder. In a scenario the thermal headroom stands on the offers that run continuously, not on oil shale, which enters the market by the day (`R-SUP-4`) and cannot start within mFRR's activation time (*revision 2.8*; ERRATA E-142, D-114).

**R-STO-8 · TSO-owned assets.** Energy Cells (LT, 200 MW, 40 MW aFRR both directions to 2026), the AST battery (LV, 80 MW: 8 MW FCR + 32 MW aFRR to 2028) and Kiisa (EE, 250 MW mFRR up / 40 down to November 2028) are outside the day-ahead fleet for the periods the Baltic TSOs' phase-out plan states (Elering 2025-11-07).

**R-STO-9 · Refit of Δ.** With reserves removed per `R-STO-7`, Δ is refitted against observed Estonian battery discharge (ENTSO-E A75 "battery", published from 2026-03-11; median 128 MWh per day to August 2026 ≈ 0.3 cycles per day, when revision 1.5 was written) and frozen; the fit and its residual are published. Having no battery data before 2026, the fit is exempt from the blind years of `R-VAL-1` (*revision 1.5*, ERRATA E-038): its window runs from 2026-03-12 to the data's last month (2026-08-31 to revision 2.7; 2026-09-30 with D-111 — *revision 2.8*), the mFRR share the owner's 0 (OPEN-3, D-025). *Revision 2.0 (ERRATA E-058):* Δ is the fit on the replay of the register in force, not a fixed figure — 65.5 €/MWh on D-025's register, 61 on D-045's, 67 on D-078's, 67.5 on D-106's, 69.5 on D-109's, 63.5 on D-111's and D-112's, 71 on D-113's and D-114's — and `fitted_parameters.json` carries it with its residual. v3's Δ = 60 €/MWh (fitted on the Hertz 1 park, April–June 2026) is the prior, which Kruonis keeps (D-022).

### 8.7 Nuclear / SMR and the contract (D6)

**R-SMR-1 · Lever.** 0, 1, 2 or 3 units in Estonia (one unit since *revision 2.6*, D-058), 300 MW each: the net output to grid, which is what the day-ahead market receives. GE Vernova Hitachi's BWRX-300 General Description (005N9751 Rev. J, June 2026) states ~300 MWe net to grid with 10–30 MWe in-house consumption (Table 21-2, p. 123) and a gross electrical output of ~316 MWe (Table 2-1, p. 28; ~315 MWe on p. 53), the figure revisions 1.0–1.2 used. The parameter is editable and both figures are shown beside it (owner, revision 1.3, D-011; OPEN-1 closed). *Revision 1.6 (D-036):* the lever is the scenario selector — *Elering: gas* (no unit), *2 SMR*, *3 SMR* — and each unit replaces 300 MW of the Estonian peaking gas of *Elering: gas*, so the three scenarios hold the same firm capacity. *Revision 2.50 (D-189):* 315 MW each, the document's gross ~315 MWe (p. 53), at the owner's choice; the net ~300 MWe stays beside it. *Revision 2.25 (D-151):* the units come on top of the fleet of the scenario without them, named *0 SMR*: the four scenarios share one base and differ only in their units.

**R-SMR-2 · Availability.** One planned outage per unit per year, duration a documented parameter (default 336 h; GE Vernova: refuelling outages of usually 10–15 days on a 12–24-month cycle and a 25-day inspection outage every 120 months, p. 51; lifetime capacity factor target 95 %, Table 21-2; the annual-equivalent duration is documented), placed in the window of largest surplus of must-run and renewable output over demand, at least 168 h apart between units. Forced outages only in the adequacy Monte-Carlo (`R-LINK-7`), with a documented forced-outage rate. Availability is therefore a result of the outage placement, not a fixed 0.92.

**R-SMR-3 · Contract designs.** The contract card offers: (a) two-sided CfD settled hourly at strike S; (b) two-sided CfD settled on the monthly average price; (c) collar 80–100 €/MWh settled hourly; (d) collar 70–110; each with and without the clause "no difference paid in hours whose price is ≤ 0" (v4 D-061). Strike S is a control, 40–160 €/MWh, default 90 (owner).

**R-SMR-4 · Dispatch follows the contract.** Under a plain two-sided CfD the operator's income is S regardless of the market price, so the plant produces whenever the price is above the floor (down to its minimum load only if the price is below its variable cost minus S, which does not occur). Under a design with the negative-price clause the plant curtails to its minimum stable load in hours with price ≤ 0. Minimum stable load (default 50 %, the lower end of GE Vernova's daily load-following range of 50–100 %, Table 21-2) is an editable parameter. *Revision 2.0 (ERRATA E-054):* no variable cost is offered or computed — under the contract the plant runs must-run, and under the clause its part above the minimum load bids the model's zero (E-052); a variable cost would matter only to an operator without a contract, which the application does not show. Precedent: TVO reduced Olkiluoto output at negative Finnish prices in 2023 (Yle, 2023-05).

**R-SMR-5 · Paired runs.** When the lever is on, every result is reported next to the same scenario with the lever off: price per zone, the plant's capture price, net import, hours in which a fossil unit or a fossil-priced import sets the price, CO₂, curtailment of wind and solar. Differences are within the pair, never across presets. *Revision 1.6 (D-036):* the three scenarios run together on the same settings; *2 SMR* and *3 SMR* are each reported against *Elering: gas*, the same scenario with the plant's capacity as gas.

**R-SMR-6 · Contract account.** For strike S and hourly output q_h: annual cost to the state Σ_h (S − p_EE,h)·q_h, negative when the market pays back, computed on the run with the plant so that the plant's own depression of p_EE is inside the figure; per design of `R-SMR-3`; shown per climate year and weighted (`R-TIME-3`); operator €/MWh and the count of settlement periods in which each side pays.

**R-SMR-7 · Restricted inputs.** The strike default and any capital-cost figure are the owner's; if they originate in a restricted Fermi document they are labelled so, and the model runs with the user's value.

**R-SMR-8 · Publication order.** The official presets (TSO and ERAA fleets and demand as published, electrolysis off per `R-DEM-5`, no plant) are the default state of the application and are shown first in every document. No result with the plant leaves the repository before the validation gate (§14) is met; every working document says so at the top. *Revision 2.13 (D-123):* or before the owner accepts the protocol's results as they stand, given on 2026-10-17; each release then states the validation beside its figures. *Revision 2.2 (D-085):* the staging site behind the password (`R-DEP-1`) counts as inside, as D16 had it; the public site does not. *Revision 1.6:* that default is *Elering: gas* — the TSO's own scenario for Estonia, ERAA's for Latvia and Lithuania.

The MAE threshold is 15, not v3's 8–12, because v3's figure was reached with the observed node price inside the model (§5, claim 1).

**R-VAL-6 · Counterfactual gate: EstLink 2.** The 2024 replay with the observed A31 profile is compared with the same year with EstLink 2 restored to 650 MW all year. The model must reproduce the sign and order of magnitude of the documented effect: Estonian average price higher by 15–30 €/MWh over the outage months (Elering: about +10 %, ≈ +18 €/MWh; Eesti Energia: +24 €/MWh in Q2 2024, +42 €/MWh in July 2024), the FI→EE congested-hour share rising from about 55 % to about 70 %, EstLink 1 near fully loaded FI→EE, and the Finnish price essentially unchanged (the boundary is exogenous; the documented Finnish effect of the 2025 outage was about −1 c/kWh on Q1 futures). The same test on 2025 (25 Dec 2024 → 19 Jun 2025) must show weekly EE–FI spreads of the order of 100 €/MWh in February 2025 (observed EE 184 vs FI 84.6 €/MWh in one week) and an annual EE–FI spread of the order of 40 €/MWh (observed 80.4 vs 40.5). A symmetric effect or an average effect under 15 €/MWh fails the gate.

**R-VAL-7 · Diagnostics without thresholds.** 2020–2022 replays are published with the same metrics as diagnostics of the fuel-based bids under the 2022 gas shock, without thresholds (BRELL topology and no reserve market then).

**R-VAL-8 · Mechanics.** `validate_fit` runs in CI on every commit that touches the engine, the export or the calibration files and fails on any threshold breach; a golden fixture pins the engine's outputs on a fixed scenario byte for byte; any movement of a calibration figure is a deliberate re-baseline with a before/after table and the owner's sign-off in `DECISIONS.md`. The protocol's current results are rendered on the application's Calibration page (`R-APP-7`).

## 10. Provenance and documentation (D15, owner's rule of 2026-09-24)

### 10.1 Provenance

**R-PROV-1 · Every number.** Every numeric input the model uses and every number the application shows can be traced to a lineage record (measured data) or to a documentary CSV row with document and page (documentary data). The export manifest carries the ids; the application shows the source on demand for every control default, preset value and result series.

**R-PROV-2 · Coverage check.** CI computes the share of model inputs with a traceable source; the build fails below 100 %. A parameter without a source may exist only as "owner's assumption" with that label in the interface and in the register, and the register lists all such parameters in one place.

**R-PROV-3 · Literature.** Every method choice justified by literature is cited in `methodology.md` with a full reference — authors, year, title, journal or publisher, volume, pages — and a DOI link where a DOI exists. References recalled from memory during the grilling are marked in §17 as "verify" and must be checked against Crossref before `methodology.md` cites them.

**R-PROV-4 · Fitted parameters.** Each fitted parameter (§9) is a number with a fit record: data used, years, method, value, residual. It is a source in its own right and appears in the register.

**R-PROV-5 · Third-party terms.** Every source's licence and access conditions are recorded as read on the fetch date; a source whose terms forbid redistribution is used only for derived quantities and is never committed (`R-DATA-10`).

**R-PROV-6 · Imported code.** Every file imported from v3 or v4 is listed in `PROVENANCE.md` with the source repository, commit hash and path.

### 10.2 Documents

**R-DOC-1 · SPECIFICATION.md** — this document. Requirements with identifiers; changes only by a new revision.

**R-DOC-2 · DECISIONS.md** — append-only, from D-001; each record: date, status, context, decision, consequences, sources; one page at most; a superseded record is marked, never edited.

**R-DOC-3 · ERRATA.md** — append-only; every error found in code, data, documents or a statement to the owner, with its effect on results and the commit or decision that fixed it, dated the day it was found. Entries are never deleted.

**R-DOC-4 · methodology.md** — the single mathematical description, rendered inside the application; every formula names the function that implements it; every limitation is listed; the fitted-parameter register (`R-VAL-2`), the LP gap table (`R-ENG-8`) and the literature (`R-PROV-3`) live here.

**R-DOC-5 · SOURCE_REGISTER.md** — generated from `pipeline/register.py` by `make register`; never edited by hand; one row per source: link or API root, access conditions, licence, what the model takes, fetch date.

**R-DOC-6 · CHANGELOG.md** — versions and what changed. No engineering log; git holds the history. *Revision 2.141 (D-328):* the changelog starts again at the first public release; the development's log stays in the author's private history.

**R-DOC-7 · AGENTS.md** — rules for anyone working in the repository, human or agent; at most two pages; the only agent-instruction file (Claude Code 2.1.277 reads `AGENTS.md` when no `CLAUDE.md` exists). No `CLAUDE.md`.

**R-DOC-8 · Entry page.** `README.md` is the repository's front page (status, read order, quick start, declaration of interest, licences, citation); it is not a rules document and states nothing that the seven documents above do not.

Documentation drift is an error: a document that describes a state the code does not have gets an `ERRATA.md` entry (v3's FAQ described four presets when the code had five; v3 carried three different figures for 2025 Estonian CO₂).

## 12. Non-functional

**R-NFR-1 · Static hosting.** The site is static files over HTTPS on the existing shared host; no server-side computation; no third-party requests at run time; no analytics or telemetry.

**R-NFR-2 · Latency.** `R-ENG-7`: the engine of record ≤ 2 s per year and ≤ 6 s per set of three years on four workers — since revision 2.16 the set of the scenario shown, computed first, the table's other scenarios after it (D-127); adequacy Monte-Carlo and the standard sensitivities (`R-APP-11`) run in the background with progress and cancel.

**R-NFR-3 · Data on demand.** One year's data is fetched when first needed and cached in memory; the page does not preload all years.

**R-NFR-4 · Size.** ≤ 3 MB compressed per year of data; JavaScript bundle ≤ v3's plus 30 %; fonts and Chart.js inside the bundle; the solver's WebAssembly module (HiGHS, about 1.2 MB compressed) outside that limit, loaded once and cached (*revision 1.4*).

**R-NFR-5 · Determinism.** The engine is byte-identical for identical inputs across runs and browsers (integer and IEEE-754 double arithmetic only; no `Math.random`, no `Date`, no locale-dependent formatting inside the engine). The adequacy sampler is seeded and reproducible.

**R-NFR-6 · Stack.** Vite; TypeScript (strict); Chart.js 4 and highs-js (HiGHS in WebAssembly, MIT; *revision 1.4*, D-021) as the only runtime dependencies; `node:test` or `vitest` for tests; no UI framework. Any new runtime dependency needs a `DECISIONS.md` record.

**R-NFR-7 · Data contract.** The year-JSON, scenario and result shapes are TypeScript types and a JSON Schema in `schema/`, shared by the Python export (which validates its output against it) and the engine (which validates its input). A schema change is a `DECISIONS.md` record.

**R-NFR-8 · Tests.** Every contract has a test: engine invariants (energy balance per zone-hour ≤ 1e-6 MW; flows within NTC; prices within [floor, VOLL]; price divergence only at saturated borders; storage SoC within bounds; nuclear energy consistent with placement; CO₂ = Σ MWh × factor), the storage heuristic on synthetic price series, the boundary rule, share-link round trip, export validation against the schema, the fetchers on hand-written samples, the loaders on a fixture database. `make test` and `make lint` pass before any hand-off.

**R-NFR-9 · Language.** Everything in English: code, comments, documents, commit messages, interface text. *Revision 2.21 (D-141):* the interface is also in Estonian, at the reader's choice — the header's button, or `?lang=et` in the address, kept in the browser — with a short Estonian translation of the questions and answers in its place; the methodology, the other documents and the data stay in English, and where the two languages differ the English text binds. A text the Estonian dictionary lacks shows in English. *Revision 2.22 (D-142):* every view is in Estonian, quotations of the sources excepted, and the methodology has a short Estonian summary beside the full English text.

**R-NFR-10 · No secrets.** Tokens and keys only in `.env` (git-ignored); `.env.example` lists the names; lineage records strip tokens.
